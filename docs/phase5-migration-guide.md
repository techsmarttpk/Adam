# Phase 5 Migration Guide: GuestControl → HTTP Guest Agent

This guide covers moving a deployment from `guest_backend = "vbox"` (the GuestControl-based
compatibility backend, default) to `guest_backend = "http"` (the guest-resident PowerShell HTTP
agent — the roadmap's originally-intended architecture). See `docs/phase5-http-agent-api.md` for
the full API contract and `docs/implementation-audit.md`'s Phase 5 section for verification
status.

## 1. Directory structure (new in this revision)

```
adam/sandbox/guest/
├── __init__.py
├── channel.py                 # NEW -- GuestChannel Protocol (the interface both backends satisfy)
├── vbox_channel.py             # NEW -- VBoxGuestChannel: thin wrapper around the existing GuestAgent
├── http_channel.py             # NEW -- HTTPGuestChannel: httpx client for the guest HTTP API
├── http_models.py              # NEW -- Pydantic models matching docs/phase5-http-agent-api.md
└── agent/
    ├── __init__.py
    ├── agent.py                 # UNCHANGED -- GuestAgent (GuestControl-based, wrapped not patched)
    ├── README.md                # NEW -- disambiguates agent.py vs. the PowerShell service below
    ├── adam_agent.ps1            # NEW -- guest-resident HTTP agent entrypoint (PowerShell 5.1)
    ├── install.ps1                # NEW -- one-time guest setup (urlacl, firewall, scheduled task)
    ├── agent.config.json          # generated by install.ps1 -- guest-local tool paths/port
    └── modules/
        ├── Common.psm1             # envelope/error helpers, Invoke-NativeProcess (no shell)
        ├── AgentConfig.psm1        # guest-local config loader
        ├── FilesystemManager.psm1
        ├── ProcessManager.psm1
        ├── ProcmonManager.psm1
        ├── NetworkManager.psm1
        ├── SysmonManager.psm1
        ├── DiagnosticsManager.psm1
        ├── SampleManager.psm1
        └── ArtifactManager.psm1
```

`adam/common/config.py` gained `Settings.guest_backend: Literal["vbox", "http"]` and
`Settings.http_guest: HttpGuestSettings`. `adam/orchestrator/runner.py` gained
`Runner._build_guest_channel()`, the sole place that branches on `guest_backend`.
`adam/orchestrator/session.py`'s `SessionOrchestrator.guest_agent` parameter is now typed
`GuestChannel | None` (was `GuestAgent | None`) — no behavioral change, only a widened type.

## 2. Migration steps

1. **Provision the guest.** Copy `adam/sandbox/guest/agent/` (or just `adam_agent.ps1` +
   `modules/` + `install.ps1`) into the guest VM, e.g. via the existing `copy_to_guest`
   GuestControl mechanism, a shared folder, or manually through the VirtualBox console.
2. **Run `install.ps1` as Administrator inside the guest.** This reserves the URL ACL for
   `HttpListener`, opens the firewall port (default 8765), writes `agent.config.json` with
   default tool paths (edit if this guest's Procmon/tshark install locations differ), and
   registers + starts a Scheduled Task so the agent survives reboots.
3. **Verify manually**: from the guest (or host, once networking allows), `curl
   http://localhost:8765/health` should return `{"success":true,"data":{"status":"ok",...}}`.
4. **Re-capture the VM's `clean` snapshot.** Every change `install.ps1` makes (URL ACL, firewall
   rule, scheduled task, `agent.config.json`) is guest-side state — `SandboxController.prepare()`
   restores the `clean` snapshot before every session, so none of this survives unless it's baked
   into that snapshot, the same rule this project's Sysmon-log-freshness design already depends
   on.
5. **Set config on the host**: in `config/<ADAM_ENV>.toml` (not `default.toml` — this is a
   per-machine value), set:
   ```toml
   guest_backend = "http"

   [http_guest]
   host = "<guest's real host-only-adapter IP>"
   port = 8765
   ```
6. **Run a session** (`adam run <sample>`) and check the logs for `guest_backend=http -- using
   HTTPGuestChannel against http://<ip>:8765` — confirms the DI wiring picked the right backend.

## 3. Rollback

Set `guest_backend = "vbox"` (or remove the line — that's the default) in the environment config
file. No other change needed; `VBoxGuestChannel`/`GuestAgent` are untouched by this revision and
remain fully operational.

## 4. Compatibility guarantees during the transition

- Both backends return identical `ToolAvailability`/`TelemetryArtifacts` dataclasses — every
  downstream consumer (`build_collectors_from_telemetry()`, `SysmonCollector`/`ProcmonCollector`/
  `NetworkCollector`) works identically regardless of which backend produced the data.
- Switching backends is a one-line config change, not a code change, in either direction.
- The two backends can coexist across different environments (e.g. `vbox` in CI/most machines,
  `http` on a machine where the guest has been provisioned) via `config/<ADAM_ENV>.toml`'s
  per-machine override tier.

## 5. Remaining Phase 5 gaps (as of this revision)

Ranked by what should be validated first:

1. **`adam_agent.ps1` has never been run.** Start it manually on a real Windows 10 guest
   (`powershell.exe -ExecutionPolicy Bypass -File adam_agent.ps1`) and confirm `/health` responds
   before trusting `install.ps1`'s scheduled-task path.
2. **`DiagnosticsManager.psm1`'s P/Invoke token code is unverified.** Call `GET
   /diagnostics/token` directly and confirm `groups`/`privileges`/`integrity_level` look sane
   (compare against `whoami /groups` + `whoami /priv` run manually in the same session — they
   should agree). If the P/Invoke path throws, it silently falls back to the whoami-parsing path
   and logs a `WARN` — check the agent's log file (`adam/sandbox/guest/agent/logs/
   adam_agent.log` relative to the install dir) for `"used whoami text-parsing fallback"`.
3. **The `/network/convert` native-redirect fix (Issue #1's PowerShell-side reimplementation)
   needs a real conversion run** — launch a capture, stop it, call `/network/convert`, and
   diff the resulting EK JSON against what `tshark -T ek > file` produces manually to confirm
   `Invoke-NativeProcess`'s stdout-stream-to-file redirect is byte-identical to shell redirection.
4. **Procmon driver-load behavior under the Scheduled-Task-as-SYSTEM launch context** —
   `install.ps1` runs the agent as SYSTEM, which (per the compatibility backend's own Issue #2
   investigation) is specifically documented to succeed at loading Procmon's driver where a
   filtered/non-elevated GuestControl token does not. This is the architecture's implicit fix for
   Issue #2/#3's whole root cause class — worth confirming explicitly: call `/procmon/start`,
   then `/diagnostics/drivers?name=procmon` to confirm the driver actually loaded, not just that
   the process launched.
5. **Load/perf characteristics are unknown** — request latency, whether the single-threaded
   `HttpListener` loop in `adam_agent.ps1` needs a multi-threaded accept loop for concurrent
   requests (SessionOrchestrator currently calls this API sequentially per session, so this may
   never matter in practice, but is unverified).
6. **Sample upload's base64/JSON scaling limit** (API spec section 10) — untested against a
   realistically large sample; the request body size `HttpListener` accepts by default may need
   raising for large samples.
7. **`collectors.ps1`** (the original roadmap's telemetry-push mechanism) was deliberately not
   built — this revision's request/response model doesn't need it. If a future phase wants live
   telemetry streaming (not just post-session file export), that would be new scope, not a gap in
   this one.

## 6. Estimated Phase 5 completion after this implementation

**~75%.** The target architecture is code-complete, internally consistent with its own written
spec, and passes 56 host-side tests plus `mypy --strict`. The remaining ~25% is entirely "run it
against a real Windows guest and fix what real hardware reveals" — the same category of gap this
project has closed for every other phase requiring a VM (compare: the compatibility backend
itself needed four real-VM rounds — Bugs #1-#4 — to go from "looks right" to "actually works").
Budget for at least one full real-VM validation pass, prioritized per the gap list above, before
switching `guest_backend` away from `"vbox"` in any environment that matters.
